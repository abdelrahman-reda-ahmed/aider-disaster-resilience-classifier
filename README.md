# AIDER Emergency-Response Image Classifier

**EE 3701 — Project 02: Artificial Neural Network Design**
**Track 1: Disaster Resilience and Emergency Response**

A from-scratch, fully reproducible deep-learning pipeline that classifies aerial
post-disaster imagery into five categories using the **AIDER** dataset.

| | |
|---|---|
| **Task** | 5-way image classification |
| **Classes** | `collapsed_building`, `fire`, `flood`, `traffic_accident`, `normal` |
| **Models** | Model A: compact CNN trained from scratch · Model B: ImageNet-pretrained MobileNetV2 (transfer learning) |
| **Framework** | PyTorch + torchvision (CPU / CUDA / Apple-MPS) |
| **Entry point** | `python run_all.py` |

Everything (code, figures, tables, report text) is generated by the scripts in
this folder — no notebook, no external repository, no hand-copied numbers.

---

## 0. Quick start — from clone to a finished run

```bash
# 1. clone
git clone https://github.com/abdelrahman-reda-ahmed/aider-disaster-resilience-classifier.git
cd aider-disaster-resilience-classifier

# 2. create and activate a virtual environment (Python 3.10+)
python -m venv .venv
#   Linux / macOS:        source .venv/bin/activate
#   Windows (PowerShell): .venv\Scripts\Activate.ps1
#   Windows (cmd):        .venv\Scripts\activate.bat

# 3. install the pinned dependencies
python -m pip install --upgrade pip
pip install -r requirements.txt
#   CPU-only Linux: install the smaller CPU torch wheels first — see §2.

# 4. run the whole project, end to end
python run_all.py
```

That one command is the entire project. It detects the device automatically
(**CUDA → Apple MPS → CPU**), trains and evaluates every experiment, and writes
everything the report needs — `results/summary.md`, `results/figures_index.md`,
all metric tables and every figure (300 dpi PNG in `figures/`).

> **The dataset ships with the repository** (`data/AIDER/`, 6,433 images in five
> class folders), so step 4 downloads nothing.  If `data/` is ever deleted, the
> pipeline re-downloads the official Zenodo archive by itself and verifies its
> MD5 against `config.AIDER_MD5`.

For a ~2-minute end-to-end sanity check instead of the full run:

```bash
python run_all.py --quick
```

**Runtime.** The full run (experiments 1–3 × seeds 42/43/44) takes a few hours
on a CPU-only laptop and much less on a GPU — measured numbers are in §6 and
`results/summary.md`.

## 1. Dataset

**AIDER — Aerial Image Dataset for Emergency Response Applications**
Christos Kyrkou and Theocharis Theocharides.
Zenodo record **3888300**, DOI **[10.5281/zenodo.3888300](https://doi.org/10.5281/zenodo.3888300)**
(license CC-BY-4.0).

The pipeline downloads the official archive directly from the Zenodo REST API:

```
https://zenodo.org/api/records/3888300/files/AIDER.zip/content
```

* archive size: `275,701,096` bytes
* archive MD5: `1ad4eb02ed156e8dfa19986ff382e58b` (verified after download)

The zip is extracted with the pure-Python `zipfile` module (no `unzip` binary
needed) into `data/`, one folder per class.  The archive names two folders
differently from the class labels used in the brief; `config.CLASS_DIR_ALIASES`
maps them automatically:

| folder in `AIDER.zip` | class label used here |
|---|---|
| `collapsed_building` | `collapsed_building` |
| `fire` | `fire` |
| `flooded_areas` | `flood` |
| `traffic_incident` | `traffic_accident` |
| `normal` | `normal` |

Real class counts measured from disk (after cleaning) are written to
`results/class_distribution.csv`; the split table is in
`results/split_table.csv`.  **The test split is never used for training,
hyper-parameter tuning, early stopping or model selection** — it is read exactly
once, by `evaluate.py`, for the final report.

## 3. Reproduce everything

```bash
python run_all.py
```

This one command performs the whole pipeline:

1. **Download + verify** the AIDER archive (resumable, MD5-checked).
2. **Integrity check + cleaning** — zero-size / unreadable files and
   cross-split duplicates (MD5) are detected and removed, per class.
3. **Stratified 70/15/15 split** (seed 42) with a programmatic assertion that
   train/val/test are disjoint by *path* **and** by *content hash*.
4. **EDA figures** — class distribution, sample grid, augmentation examples.
5. **Model summaries** — parameter counts, on-disk size, layer listings,
   warmed-up inference time per image, architecture diagrams.
6. **Training** — experiments 1–3 × seeds 42/43/44, each in its own subprocess.
7. **Final evaluation** of the selected checkpoints on the test split.
8. **Report** — `results/summary.md` and `results/figures_index.md`.

Useful flags:

| flag | meaning |
|---|---|
| `--quick` | tiny end-to-end smoke run (a few epochs, one seed) |
| `--jobs N` | how many trainings run in parallel (default 3) |
| `--force-data` | re-download and re-clean the dataset |
| `--experiments a,b` | restrict which experiments to run |
| `--seeds 42,43` | override the seed list |

Individual steps can also be run on their own:
`python data.py`, `python train.py --exp exp2_modelB_aug --seed 42`,
`python evaluate.py`.

Resume is automatic: a training run is skipped if its checkpoint **and** its
history CSV already exist, so an interrupted `run_all.py` can simply be
re-launched.

## 4. Experiments

All experiments use the **same fixed split**.

| id | model | augmentation | role |
|---|---|---|---|
| `exp1_modelA_aug` | Model A (from scratch) | yes | baseline |
| `exp2_modelB_aug` | Model B (MobileNetV2) | yes | **main model** |
| `exp3_modelB_noaug` | Model B (MobileNetV2) | no | required augmentation ablation |
| `exp4_modelA_noaug` | Model A (from scratch) | no | optional extra ablation |

Each of experiments 1–3 is repeated with seeds **42, 43, 44** and reported as
mean ± std.  `evaluate.py` performs the error analysis for the main model
(hardest class, most frequent confusion pairs, misclassified-example grid,
Grad-CAM heat-maps).

### Training protocol

* optimizer **AdamW** (`weight_decay = 1e-4`); class-weighted cross-entropy
  (weights computed from the **train** split only)
* batch size 32, images resized to **224×224**, ImageNet normalization
* augmentation (train only): random horizontal flip, ±15° rotation,
  `RandomResizedCrop(scale=(0.7, 1.0))`, colour jitter (brightness/contrast 0.2);
  validation/test get resize + normalize only
* **Model A**: lr 1e-3 with cosine annealing to 1e-5, up to 30 epochs
* **Model B**: stage 1 — backbone frozen, new head, lr 1e-3 (4 epochs);
  stage 2 — full fine-tune, lr 1e-4 cosine-annealed to 3e-5 (up to 16 epochs)
* **early stopping on validation macro-F1** (patience 6), best checkpoint by
  validation macro-F1 is the one evaluated
* mixed precision is enabled only when running on CUDA

## 6. Hardware, runtime and device selection

The device is chosen automatically: **CUDA → Apple MPS → CPU**.  Mixed
precision and `pin_memory` are used only on CUDA.

The reference run in this repository was produced on:

| | |
|---|---|
| CPU | Intel Core i7-11800H, 8 cores / 16 threads @ 2.3 GHz |
| RAM | 23 GiB |
| GPU | none (CPU-only run) |
| OS | Debian (Linux 6.12) |
| Python / torch | 3.13 / 2.14.1+cpu |

On this CPU-only machine a full epoch takes roughly **175 s for Model A** and
**110 s (frozen) / 250 s (fine-tune) for Model B**; the complete
experiments-1–3 × 3-seeds run therefore takes a few hours.  The measured
wall-clock time of the reference run is recorded in `results/summary.md`.

> **CPU-only note.** This box is memory-bandwidth bound: one DataLoader/worker
> configuration is essentially as fast as many, and *oversubscribing* PyTorch
> threads (using all 16 hardware threads) is ~2× **slower** than using 4–8.
> `run_all.py` therefore sizes the thread count from the number of parallel
> jobs (`threads = cpu // jobs`).  On Windows the DataLoader worker count is
> capped at 2 because every worker is a fresh spawned interpreter.

## 7. Reproducibility

* `utils.set_seed(42)` seeds Python, NumPy and PyTorch at the start of every
  entry point; DataLoader workers are re-seeded deterministically through a
  `worker_init_fn`.
* On CUDA, cuDNN is put into deterministic mode
  (`torch.backends.cudnn.deterministic = True`, `benchmark = False`); on CPU
  every operation this project uses is already single-threaded-deterministic
  given the seeds.  `torch.use_deterministic_algorithms` is deliberately *not*
  forced, because it can select much slower CPU kernels for no accuracy benefit.
* DataLoader shuffling uses a seeded `torch.Generator`, so the exact same
  batches are produced for a given seed.
* The split is fixed in `results/splits.csv`; every experiment reads it.
* Small run-to-run differences can still arise from non-deterministic CPU
  reductions and from mixed-precision arithmetic on GPU — multi-seed mean ± std
  is reported precisely because of this.

## 8. Project layout

```
project/
  config.py      single source of truth: paths, hyper-parameters, seeds
  utils.py       seeding, plotting style, timers, small helpers
  data.py        download / extract / clean / split / datasets / EDA figures
  models.py      Model A, Model B, layer summaries, timing, architecture figure
  train.py       training loop, validation-macro-F1 early stopping, CLI
  evaluate.py    final test metrics, confusion matrices, ROC, error analysis, Grad-CAM
  run_all.py     end-to-end orchestrator + summary.md + figures_index.md
  requirements.txt
  README.md
```

`utils.py` is an addition to the brief's file list; it exists so that seeding,
plotting style and timing live in exactly one place instead of being duplicated
across the four scripts.
